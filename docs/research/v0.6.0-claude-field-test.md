# SafeLane v0.6.0 Claude field test

Date: 24 August 2026  
Application: `AndrewMaged814/safelane-demo-api`  
Environment: local Minikube registered as `production`

## Outcome

Registration and assessment completed. The approved Release Run did not touch
the cluster. Its immediate pre-mutation recheck failed when SafeLane exhausted
GitHub's anonymous API allowance even though GitHub CLI was authenticated.

The field test therefore proved the safe failure boundary, but it did not prove
an end-to-end release.

## Findings

### P0 — Release Run silently ignores existing GitHub CLI authentication

SafeLane constructs its GitHub client from `GITHUB_TOKEN` only. It does not read
`GH_TOKEN` and does not use the authenticated GitHub CLI credential. `gh api`
had its authenticated allowance available while SafeLane's anonymous allowance
was exhausted.

The failure happened after the user approved the recommendation. No mutation
occurred, and the Approval remained unspent, which is correct. The experience
is still a release blocker because the required credential was neither checked
at registration nor stated before approval.

Recommended correction:

1. Resolve authentication once with an explicit precedence: `GITHUB_TOKEN`,
   `GH_TOKEN`, then the authenticated GitHub CLI credential.
2. Report the authentication source without printing the credential.
3. Fail before assessment when authenticated GitHub access required for the
   eventual recheck is unavailable.
4. Test inspect and run with the same credential resolver.

### P0 — Run revalidation repeats the entire inspection

The pre-mutation check calls `FreezeDelta` again. That repeats repository
settings, checks, the full source comparison, candidate lookup, registry reads,
cluster discovery, and health collection even though Approval recheck compares
only revision, digest, running image, configuration, Rollout identity/version,
patch, and analysis definition.

This made an unrelated source-comparison request a release-time dependency and
caused the 403 that blocked this run. Revalidation should read the smallest set
of material facts represented by `releasepatch.Facts`; it should not rebuild the
complete Release Delta.

### P0 — Citation validation can accept a claim that its evidence does not say

Claude manually concluded that the selected image was not a deliberately broken
fixture, then cited a new name that was outside SafeLane's evidence package.
SafeLane correctly rejected that citation. Claude corrected the structure and
the final recommendation repeated the claim.

Validation currently proves only that a cited evidence ID exists. It cannot
prove that the cited view entails the statement. This permits evidence
laundering: an unsupported statement can pass after its citation is renamed to
an allowed view.

SafeLane must not claim semantic validation it does not perform. Near-term
mitigations are to narrow what the skill may assert, make external investigation
an explicit typed evidence source, and test correction attempts that preserve an
unsupported claim while changing only its citation.

### P1 — Registration has no agent-usable selection contract

Discovery returns repository, context, Rollouts, containers, compatibility,
analysis, and fingerprint. Registration expects a separate flat object with
exactly `application`, `environment`, `impact`, `context`, `namespace`,
`rollout`, `container`, and `fingerprint`. Neither `discover` nor
`register --help` emits that schema or a ready selection skeleton.

Claude made three avoidable attempts:

1. It copied `repository` from discovery; strict decoding rejected the unknown
   field.
2. It nested Environment name and impact; registration expects flat fields.
3. It omitted Application; registration tried to resolve an already registered
   Application, which cannot work during first registration.

Recommended correction: discovery should return registration candidates or a
machine-readable selection schema with only the fields registration accepts.
The agent should fill only Environment name and impact when target/container are
unambiguous.

### P1 — Registration depends on the caller's current directory

Claude created the selection in a scratch directory and invoked registration
there. SafeLane could not read the Application's GitHub origin. The skill says
to run registration but does not explicitly anchor every command to the
Application repository.

Recommended correction: state the repository-root invariant in the skill and
carry the discovered repository through a registration session so preview does
not depend on the selection file's working directory.

### P1 — The assessment escaped SafeLane's evidence boundary

After inspection, Claude ran raw `git diff`, read complete source files, read
the live Rollout YAML, inspected the workflow, and queried registry tags. The
skill says both to use read-only repository tools for a named question and not
to expose arbitrary raw source. That is ambiguous, and the CLI does not enforce
the boundary in a normal Claude session.

The result took more than eight minutes and introduced facts SafeLane could not
represent. The production workflow did not behave like the bounded assessment
evaluation that the test suite exercises.

Recommended correction:

- make the four compact views available as explicit small commands or files;
- remove the contradictory repository-tool instruction;
- allow only typed on-demand evidence for claims that need more detail;
- state that unavailable semantics become one focused question or uncertainty,
  not a general repository investigation.

### P1 — The final assessment mixed strong and weak hazards

The replica-granularity finding was material: with two replicas and no traffic
router, a nominal 25 percent step approximates 50 percent serving capacity.

The request-count finding was conditional. A per-pod reset is harmful only if a
consumer treats the value as a durable or global count; no consumer evidence
was established. It should have been omitted or expressed as an unresolved
precondition.

The idle-traffic finding described a safe analysis behavior, but this demo
installs continuous load. Presenting it as a current concern without checking
that prerequisite made the assessment less focused.

### P2 — Build confirmation is expected, but poor for the demo path

The OCI Artifact identifies its source revision but not the exact GitHub
workflow that published it. SafeLane correctly asked the user to select the one
successful workflow and bound that confirmation to the candidate and digest.

This is not a SafeLane correctness defect. For a rehearsed demo, the application
workflow should publish verifiable provenance or an attestation so the ordinary
path does not need this question.

### P2 — Missing branch protection was reported correctly

The default branch has no required checks. SafeLane correctly reported that it
had no required-check policy to verify and did not misrepresent a successful
workflow as a required check. Configure branch protection before the demo if
required checks are part of the product claim.

### P2 — Safe failures behaved correctly

- Discovery refused to invent a Deployment Target when kubeconfig had no
  current context.
- Strict registration rejected unknown fields.
- Assessment rejected an unknown evidence citation and allowed one correction.
- Registration changed no Kubernetes resources.
- Release Run rechecked facts before mutation.
- The failed recheck changed no Rollout and did not spend the Approval.

These are positive boundary results, not defects.

## Demo bootstrap defects

Three defects were independently reproduced and fixed after this field test:

1. Fresh setup checked cluster-admin access before starting Minikube.
2. Git Bash process substitution produced a `/proc` or `/dev/fd` path that
   native Windows Helm could not open.
3. The required Argo Rollouts kubectl plugin was discovered only after cluster
   resources had already been created.

The Windows guide also now invokes Git Bash explicitly so PowerShell cannot
open `install.sh` through its file association.

## Recommended order

1. Fix shared GitHub authentication and minimal pre-mutation revalidation.
2. Make registration emit a ready selection contract.
3. Close the gap between the tested assessment boundary and real agent tools.
4. Strengthen the demo repository with provenance and required checks.
5. Only then tune wording or add more assessment signals.

## Corrections implemented after the field test

The first three priorities were implemented together because they formed one
agent workflow failure:

- GitHub credentials now resolve from `GITHUB_TOKEN`, then `GH_TOKEN`, then an
  existing authenticated `gh` session. The token is never printed or stored.
- Release Run no longer rebuilds the Release Delta. Immediately before
  mutation it re-reads the live Rollout, running image, analysis definition,
  local release settings, and exact patch inputs represented by Approval.
- Discovery now emits flat, copy-ready `registration_candidates`. The agent
  supplies only the Environment name and impact, and the skill keeps every
  command anchored at the Application repository root.
- The skill now treats the frozen Delta as the assessment boundary. It removes
  the contradictory raw-repository instruction, limits follow-up reads to
  listed evidence handles, and requires unsupported claims to be removed rather
  than retained with a renamed citation.
- Conditional failure modes whose material preconditions are unavailable are
  asked only when they could change the recommendation; otherwise they are
  omitted.

Semantic entailment checking remains future work. The current correction is an
agent contract and regression guard, not a claim that SafeLane can prove the
meaning of arbitrary prose.
