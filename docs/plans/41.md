# SafeLane release assessment and registration redesign

## User Story

Reference: [#41 — Lock the smallest convincing SafeLane demonstration](https://github.com/safelane-dev/safelane/issues/41).

Replace the demo-specific setup and pull-request release workflow with the smallest convincing Application-to-Environment release experience. This plan supersedes the older product assumptions in #41 and #59 where they conflict with the decisions recorded here.

## Problem Statement

SafeLane can coordinate an Argo Rollout, but a new user cannot practically adopt the current product. Setup generates demo-shaped project, policy, analysis, and manifest files; release starts from a merged pull request rather than an Application and Environment; GHCR and template assumptions exclude otherwise compatible repositories; and the current assessment combines fixed heuristics with nested model execution instead of explaining the real deployment hazards of the complete candidate.

The result is technically substantial but not a credible general POC. A judge cannot point SafeLane at an existing Argo canary, understand a concise recommendation, approve it naturally, and watch the exact release complete.

## Solution

SafeLane becomes a registration and release-coordination layer over an existing Argo Canary Rollout.

Setup discovers mechanical facts from Git, the current Kubernetes context, and the selected namespace. The user confirms the Application, Environment, Rollout, container, and Environment impact. SafeLane writes one minimal `safelane.yml` with product defaults. It does not provision resources, generate health analysis, or generate operational YAML.

At release time, SafeLane resolves the exact candidate Artifact, deployed baseline, complete source change, CI result, Deployment Target, configured background analysis, and compact relevant history into a frozen Release Delta. The active Claude session performs one bounded deployment assessment. It asks no questions when the evidence is enough and asks one plain, material question at a time only when the answer can affect the recommendation.

Claude recommends either proceeding or waiting. A proceeding recommendation maps an internal Low, Medium, or High assessment to one configured Release Lane. SafeLane validates and freezes the recommendation, shows the user understandable evidence and the actual rollout sequence, obtains one explicit approval, rechecks material facts, and patches only the selected container image and Argo canary steps. Argo owns health evaluation and rollback; SafeLane coordinates progression, status, hold, continue, stop, and compact proof.

## Definition of Done

From a registered, compatible Argo Rollout, a user can ask Claude to release an Application to an Environment; SafeLane identifies the exact candidate and accumulated changes, produces a concise evidence-based recommendation with only necessary follow-up questions, applies the approved container and rollout sequence, monitors its configured health analysis, supports status/hold/continue/stop, and stores compact release proof.

## User Stories

1. As a user, I want to register an existing Application without learning SafeLane's old project, policy, and template concepts, so that setup feels adoptable.
2. As a user, I want setup to use my current Kubernetes context and one namespace, so that SafeLane does not scan or switch clusters behind my back.
3. As a user, I want SafeLane to list the Argo Rollouts I can read, so that I can select the real Deployment Target.
4. As a user, I want SafeLane to list the inline containers in the selected Rollout, so that I can select the Artifact SafeLane will release.
5. As a user, I want to name the Environment and state its impact, so that Claude does not infer importance from names such as `production` or `staging`.
6. As a user, I want to preview the complete registration before SafeLane writes it, so that setup is explicit and reversible.
7. As a user, I want rerunning setup to show a meaningful diff, preserve my configured lanes, and do nothing when facts are unchanged, so that setup has a maintenance cycle.
8. As a user, I want one readable `safelane.yml`, so that I can understand and manually maintain SafeLane's small configuration surface.
9. As a user, I want SafeLane to ignore old configuration rather than silently migrate it, so that the POC has one unambiguous contract.
10. As a user, I want to request “Deploy payments-api to production,” so that release starts from my intent rather than a pull-request number.
11. As a user, I want to optionally name an exact source revision, so that I can release a known candidate without making a pull request the release object.
12. As a user, I want the default candidate to be the exact current head of the registered repository's default branch, so that “current” has one deterministic meaning.
13. As a user, I want SafeLane to verify that the selected container was produced from the successful candidate build, so that the tested version and deployed version cannot silently differ.
14. As a user, I want SafeLane to compare the running version with the candidate, so that the assessment covers every included change rather than only the last pull request.
15. As a user, I want a one-time confirmed baseline when the running Artifact has no usable source metadata, so that SafeLane can bootstrap honestly without fabricating provenance.
16. As a user, I want registry-neutral OCI support using anonymous access or existing Docker credentials, so that SafeLane is not restricted to public GHCR images.
17. As a user, I want eligibility failures reported separately from deployment risk, so that failed CI or an untraceable Artifact is not disguised as “high risk.”
18. As a user, I want Claude to assess the exact Artifact, Environment, rollout mechanism, health analysis, and relevant history, so that the recommendation is about deployment rather than generic code quality.
19. As a user, I want Claude to investigate available read-only evidence before asking me, so that I am not used as a search engine.
20. As a user, I want zero assessment questions when the evidence is sufficient, so that the normal release path remains fast.
21. As a user, I want only one focused question at a time when a material fact is unavailable, so that the assessment does not feel like a questionnaire.
22. As a user, I want every question to explain the missing fact and why it matters in release language, so that I can answer without understanding SafeLane terminology.
23. As a user, I want “I don't know” to be valid, so that SafeLane carries uncertainty into its recommendation instead of repeatedly questioning me.
24. As a user, I want a recommendation to say “proceed” or “wait,” so that I do not have to interpret a third decision state.
25. As a user, I want the recommendation to explain whether the version passed, whether the prepared container came from that build, and whether included changes require extra precautions, so that I understand why SafeLane is confident.
26. As a user, I want only deployment-relevant hazards in the report, so that style findings and speculative warnings do not create noise.
27. As a user, I want credible hazards related to the health analysis that can detect them, so that a slower lane is connected to real controls rather than ceremony.
28. As a user, I want the proposed rollout shown as actual percentages and checks, so that a lane name is never the only explanation.
29. As a user, I want internal risk labels, record IDs, hashes, and schema versions hidden by default, so that SafeLane speaks release language.
30. As a user, I want to ask “why?” without rerunning the assessment, so that I can inspect its reasoning cheaply.
31. As a user, I want corrected or newly provided evidence to revise only the affected assessment, so that the loop remains responsive.
32. As a user, I want an approved recommendation to bind one exact candidate, target, patch, analysis, and assessment, so that approval is not reusable.
33. As a user, I want SafeLane to recheck material facts immediately before mutation, so that approval cannot apply after the candidate or target changed.
34. As a user, I want SafeLane to modify only the selected container image and configured percentage steps, so that it preserves my probes, resources, Services, router, analysis, and application settings.
35. As a user, I want SafeLane to use my existing background Argo analysis, so that my Application owns the definition of health.
36. As a user, I want SafeLane to remain attached while the rollout progresses, so that I can see the current step and terminal outcome.
37. As a user, I want to say status, hold, continue, or stop without supplying internal IDs, so that I control the active release naturally.
38. As a user, I want one active release per Application and Environment, so that those natural controls are unambiguous.
39. As a user, I want a compact view of the latest ten releases for the same Application and Environment, so that history helps without consuming the Claude session.
40. As a reviewer, I want the final assessment and proof stored separately from compact history, so that audit detail remains available on demand.
41. As a reviewer, I want assessment observations to cite frozen evidence and inferences to state their preconditions, consequence, and coverage, so that persuasive prose cannot replace grounding.
42. As a reviewer, I want repository content treated as evidence rather than instructions, so that prompt injection in a diff, commit message, analysis name, or history cannot approve or execute a release.
43. As a maintainer, I want an assessment scenario suite covering both easy and adversarial releases, so that recommendation quality is evaluated before the demo.
44. As a demonstrator, I want Ahmed's external cluster package to remain reproducible and product-independent, so that SafeLane does not regain cluster ownership.
45. As a demonstrator, I want the first-party demo and a differently shaped official Argo example to pass the same discovery contract, so that compatibility is not merely asserted.
46. As a user, I want registration to end by showing what it registered, what it will watch, what it will never change, and the exact first release request I can make, so that I know SafeLane is ready without reading the file.
47. As a user, I want status to name where the release currently is and what it is waiting for, so that a long release is never opaque.
48. As a reviewer, I want secret values excluded from frozen evidence and stored proof, so that release records are safe to keep and share.
49. As an agent and as a person, I want short commands that infer the Application and the active release, so that the same surface is cheap for Claude to call and pleasant to type by hand.

## Implementation Decisions

### 1. Canonical domain and architectural records

Before feature code, update `CONTEXT.md` and add `docs/adr/0006-registration-and-agent-assessment.md`.

ADR 0006 supersedes the conflicting parts of:

- `docs/adr/0003-risk-selects-the-lane.md`: remove deterministic heuristics, worse-of combination, agent-authorship floors, and automatic Guarded fallback. Preserve the separation between deterministic eligibility and semantic deployment assessment, plus configured risk-to-lane mapping.
- `docs/adr/0005-safelane-owns-setup.md`: replace setup compilation and SafeLane-authored Runtime Assertions with deterministic registration of application-owned rollout infrastructure and analysis.

ADR 0001 remains valid: SafeLane does not scan rendered YAML. ADR 0004 remains valid: SafeLane coordinates and Argo executes analysis, abort, and rollback.

Revise the glossary around these canonical terms:

- **Release Delta** replaces Change Dossier: deployed source `A`, candidate source `D`, the complete `A...D` change, immutable Artifact identity, proposed Release Patch, Deployment Target, configured health analysis, compact history, and provided evidence.
- **Release Recommendation**: the frozen assessment outcome, evidence references, credible hazards, internal risk, selected configured lane when proceeding, and plain-language rationale.
- **Release Patch** replaces Rendered Manifest Bundle: one JSON Patch that may replace only the selected container image and `spec.strategy.canary.steps`.
- **Configured Health Analysis** replaces SafeLane-authored Runtime Assertions: the background AnalysisTemplate references already owned by the Application's Rollout.
- Remove Semantic Findings and Setup Plan from the active product language.
- Use action-based evidence language: configured, discovered, confirmed, provided, approved.

### 2. One configuration file and deterministic locations

Replace `internal/project` and the configuration half of `internal/policy` with a single deep module, `internal/config`:

```go
type Config struct {
    Application  Application       `yaml:"application"`
    Artifact     Artifact          `yaml:"artifact"`
    Environments []Environment     `yaml:"environments"`
    Policy       Policy            `yaml:"policy"`
}

type Application struct {
    Name       string `yaml:"name"`
    Repository string `yaml:"repository"`
}

type Artifact struct {
    Container string `yaml:"container"`
    Image     string `yaml:"image"`
}

type Environment struct {
    Name       string     `yaml:"name"`
    Impact     Impact     `yaml:"impact"` // low | significant | critical
    Kubernetes Kubernetes `yaml:"kubernetes"`
}

type Kubernetes struct {
    Context   string `yaml:"context"`
    Namespace string `yaml:"namespace"`
    Rollout   string `yaml:"rollout"`
}

type Policy struct {
    DefaultLane string          `yaml:"default_lane"`
    RiskMapping map[Risk]string `yaml:"risk_mapping"`
    Lanes       map[string]Lane `yaml:"lanes"`
}

type Lane struct {
    Weights []int `yaml:"weights"`
}
```

The exact generated shape is:

```yaml
application:
  name: payments-api
  repository: acme/payments-api

artifact:
  container: payments-api
  image: ghcr.io/acme/payments-api

environments:
  - name: production
    impact: critical
    kubernetes:
      context: safelane-caller-payments-api
      namespace: payments
      rollout: payments-api

policy:
  default_lane: guarded
  risk_mapping:
    low: fast
    medium: standard
    high: guarded
  lanes:
    fast:
      weights: [50, 100]
    standard:
      weights: [25, 50, 100]
    guarded:
      weights: [25, 50, 75, 100]
```

There is no schema version, controller credential path, default branch, required-check name, image-tag pattern, template path, analysis configuration, or semantic heuristic configuration.

`internal/config/locations.go` resolves:

```text
~/.safelane/apps/<application>/safelane.yml
~/.safelane/apps/<application>/environments/<environment>/identities/controller/kubeconfig
~/.safelane/apps/<application>/environments/<environment>/releases/
~/.safelane/apps/<application>/environments/<environment>/history.jsonl
```

The caller remains the current external kubeconfig context. The controller kubeconfig path is derived, never read from YAML. Old `project.yml`, `policy.yml`, `process.yml`, `release-template/`, setup plans, and old app-level release stores are ignored. SafeLane prints one instruction to rerun setup and never deletes user-home files automatically.

### 3. Registration-only setup

Replace the current `internal/setup` snapshot/findings/compiler with `internal/discovery` plus a small registration service.

The agent-facing internal command sequence is:

```text
safelane discover <namespace>
safelane register <selection-json-path|->
```

The skill hides commands and asks for confirmation in plain language. The command surface rules in decision 11 apply to both.

`Discover(ctx, namespace)`:

1. Reads the GitHub repository from Git origin.
2. Reads the current kubeconfig context with `kubectl config current-context` and never changes it.
3. Calls the Kubernetes API through `kubectl get rollouts.argoproj.io -n <namespace> -o json`.
4. Returns every readable Rollout and each `.spec.template.spec.containers[]` name and image dynamically.
5. After target selection, reads the exact Rollout, referenced stable/canary Services, and every background AnalysisTemplate reference.
6. Detects and explains unsupported shapes: blue-green, `workloadRef`, missing inline container, no background analysis, unresolved Service or AnalysisTemplate, advanced unsupported step/plugin shapes, or known Argo CD/Flux ownership.
7. Separately reports Environment compatibility and Artifact traceability readiness.

`RegistrationSelection` contains only explicit answers and discovery fingerprints:

```go
type RegistrationSelection struct {
    Application string `json:"application"`
    Environment string `json:"environment"`
    Impact      Impact `json:"impact"`
    Context     string `json:"context"`
    Namespace   string `json:"namespace"`
    Rollout     string `json:"rollout"`
    Container   string `json:"container"`
    Fingerprint string `json:"fingerprint"`
}
```

Registration re-reads and fingerprint-checks the selected resources, derives the image repository by removing the selected live image's tag/digest, applies the three compiled default lanes, previews the full file/diff, and writes with a temporary file plus atomic rename. Reconciliation updates discovered Application/Artifact/Environment facts only after confirmation and preserves the existing `policy` block byte-for-byte through a YAML node merge. An unchanged registration is a no-op. Environment removal remains an explicit later operation, not an accidental result of discovery.

Registration ends with the short readiness summary fixed as **A1** in Appendix A, rather than a written-file confirmation. The skill states the Application and Environment it registered, the Rollout and container it will release, the background health analysis it will watch, the fact that it will change only the container image and the canary steps, and the exact sentence the user can say next, such as "Deploy payments-api to production." This is presentation over the deterministic registration already described; it adds no discovered configuration, no generated resources, and no suggested schedules or guardrails.

### 5. Registry-neutral Artifact and source resolution

Replace `internal/verify/ghcr` with `internal/verify/oci` backed by `github.com/google/go-containerregistry/pkg/v1/remote` and standard Docker credential discovery.

Expose this port at the orchestration seam:

```go
type OCI interface {
    Resolve(ctx context.Context, repository, reference string) (Artifact, error)
    FindRevision(ctx context.Context, repository, source, revision string) (Artifact, error)
    ReadSource(ctx context.Context, artifact Artifact) (SourceMetadata, error)
}
```

Rules:

- accept any OCI Distribution-compatible registry reachable anonymously or through existing Docker credentials;
- resolve every selected tag to an immutable digest before assessment;
- inspect every runnable platform in an OCI index and require consistent full `org.opencontainers.image.revision` and `org.opencontainers.image.source` values when labels are the evidence source;
- allow CI metadata/provenance or prior SafeLane history to provide the same binding;
- never infer a revision from timestamps, tag spelling, or digest similarity;
- use tag enumeration plus verified OCI source labels to find the Artifact for a requested revision; if the registry cannot expose a matching Artifact, require an exact Artifact reference rather than choosing an older candidate;
- record the binding method (`oci_labels`, `ci_provenance`, `safelane_history`, or `confirmed_baseline`) in evidence.

For the one-time baseline fallback, the user provides an exact deployed commit. SafeLane verifies that the commit exists in the registered repository, binds it to the currently observed digest as `confirmed_baseline`, and treats the first assessment cautiously. Later SafeLane-owned history provides exact baselines.

### 6. Candidate, CI, and complete-change evidence

Rework `internal/verify/github` away from pull-request facts. Add:

```go
type Source interface {
    Repository(ctx context.Context, owner, name string) (Repository, error)
    DefaultHead(ctx context.Context, repository string) (Revision, error)
    Revision(ctx context.Context, repository, sha string) (Revision, error)
    Compare(ctx context.Context, repository, base, head string) (Comparison, error)
    Checks(ctx context.Context, repository, sha string) (Checks, error)
}
```

Candidate selection is the exact default-branch head observed at release start unless the user names an exact revision. The revision must belong to the registered repository and default-branch history.

Eligibility requires:

- an exact candidate source revision;
- the image-producing workflow for that exact revision succeeded;
- every GitHub required check for that revision passed;
- the selected OCI Artifact binds to that revision and registered source repository;
- an exact deployed source revision is available;
- the candidate is not older than or unrelated to the deployed revision.

When branch protection exposes no required checks, provenance that binds the digest to a GitHub Actions run may identify the successful image-producing workflow directly. Without that provenance, list only successful workflow runs for the exact candidate and ask the user to confirm which one produced the selected image. Store that confirmation as release-scoped evidence, not configuration. Report the missing branch protection in either case. Pending/failed checks, a failed head build, unrelated histories, an unconfirmed build, or an untraceable Artifact stop before semantic assessment; SafeLane never substitutes an older green candidate.

Use GitHub's compare endpoint or equivalent Git data to construct the complete `A...D` comparison, including all commits and pull requests represented by that range. Pull requests appear only as provenance summaries.

### 7. Frozen Release Delta and progressive evidence views

Add `internal/delta` as the single immutable evidence boundary:

```go
type ReleaseDelta struct {
    SnapshotID  string
    Application string
    Environment string
    Baseline    ArtifactBinding
    Candidate   ArtifactBinding
    Changes     ChangeSet
    Deployment  DeploymentEvidence
    Health      []HealthObjective
    History     []HistoryCard
    Provided    []ProvidedEvidence
    Patch       ReleasePatch
    CapturedAt  time.Time
}
```

The snapshot ID is a content hash used internally. Claude receives stable evidence handles, not mutable file paths masquerading as evidence.

Always expose four concise views:

```text
changes      complete A...D summary, commits, and changed files
deployment   Environment impact, Rollout mechanism, selected container, and proposed patch
health       normalized background analysis names, providers, conditions, timing, and scope
history      at most ten compact cards for this Application and Environment
```

Provide only typed, secret-safe AnalysisTemplate structure and older/cross-Environment history on demand. SafeLane does not persist or return arbitrary raw source. The skill uses the compact commit/path range and asks one named deployment question when that is insufficient. It must not perform a general code review, style review, fix design, or configuration generation.

Source text, commit messages, analysis names, and history are explicitly marked untrusted evidence. They cannot authorize mutation and cannot change the fixed assessment objective.

Secret values never enter the Release Delta. SafeLane reads the complete Rollout but retains only typed names and references, excluding container environment values, `envFrom` and mounted Secret/ConfigMap contents, kubeconfig contents, and registry credentials. It never persists or returns raw source diffs. On-demand AnalysisTemplate evidence retains structure and an explicit allowlist of assessment fields; every other scalar value, including arguments and provider configuration, is omitted before storage. This is exclusion at the evidence boundary rather than redaction at render time, so a value that is never captured cannot later reach the assessment, stored proof, or terminal.

### 8. Active-Claude assessment contract

Remove nested Claude/Codex execution, `internal/assess/heuristic.go`, `internal/assess/worse.go`, model fallback, path/size/agent-authorship floors, model configuration, and risk arithmetic.

Keep one structured assessment module, `internal/assessment`, which validates the active Claude session's final result:

```go
type Recommendation struct {
    SnapshotID      string           `json:"snapshot"`
    Observations    []Observation    `json:"observations"`
    Hazards         []Hazard         `json:"hazards"`
    HistoryFindings []HistoryFinding `json:"history_findings,omitempty"`
    Risk            Risk             `json:"risk"`   // low | medium | high | undetermined
    Action          Action           `json:"action"` // proceed | wait
    Lane            string           `json:"lane,omitempty"`
    Rationale       string           `json:"rationale"`
    Provided        []ProvidedEvidence `json:"provided_evidence,omitempty"`
}

type Hazard struct {
    Name          string     `json:"name"`
    Evidence      []Handle   `json:"evidence"`
    Preconditions []string   `json:"preconditions"`
    Consequence   string     `json:"consequence"`
    Coverage      Coverage   `json:"coverage"`
}

type Coverage struct {
    Status      CoverageStatus `json:"status"` // covered | partially_covered | not_covered | unknown
    Evidence    []Handle       `json:"evidence,omitempty"`
    Explanation string         `json:"explanation"`
}
```

The validator enforces schema, snapshot identity, valid evidence handles, configured lane names, risk-to-lane mapping, observation citations, hazard causal fields, and coverage structure. It does not attempt to judge semantic correctness with deterministic path rules.

Environment impact is context for Claude's explanation. It never adds a fixed risk increment, creates a minimum risk, or selects a lane by itself.

An `undetermined` risk or a failed assessment receives one correction attempt in the active session. If it still cannot produce a valid, grounded recommendation, SafeLane recommends waiting. It never automatically falls back to Guarded.

The adaptive assessment loop belongs in `internal/skill/SKILL.md`:

1. Read the four mandatory evidence views.
2. Build an internal frontier of unresolved deployment decisions.
3. Investigate an available read-only source before asking the user.
4. Ask one plain question only if the missing fact is material and unavailable elsewhere.
5. State the missing fact and why it matters; never mention how an answer may change an internal risk or lane.
6. Accept “I don't know,” carry the uncertainty, and never repeat the question.
7. Use each answer to prune or reshape the frontier.
8. Stop immediately once the recommendation is supportable. Zero questions is normal.

User-provided facts are attached to the final frozen snapshot with source, time, candidate, and Environment. Conversation text, drafts, and tool traces are not persisted as release history.

### 9. Plain-language recommendation and approval

The exact text SafeLane prints is fixed by the output contract in Appendix A, so that a dozen separate implementation sessions produce one voice. A successful result renders as **A2**, immediately followed by **A5**, which states what SafeLane will not touch.

A waiting recommendation renders as **A3**. It names the concrete deployment consequence, the missing or uncovered evidence, what the configured analysis cannot detect, and one suggested next step. It may offer to reassess after evidence is provided or to record a reasoned exception and propose the most cautious configured lane.

Do not show Low/Medium/High, recommendation IDs, release IDs, hazard IDs, schema versions, hashes, commit placeholders such as “D,” or commands unless the user asks for technical details. Exact revisions and digests remain in proof.

Natural approval is contextual. `approve`, `go ahead`, `release it`, and `yes, proceed` are valid. A bare `yes` is valid only as the direct answer to the final approval question. Earlier assessment agreement is never approval.

Explanation does not invalidate a recommendation. New evidence creates a revised frozen recommendation and invalidates the old approval opportunity. A waiting recommendation must be revised to an executable proceeding recommendation before it can be approved.

### 10. One exact Release Patch

Delete `internal/render`, embedded Release Templates, rendered bundles, template hashes, template identity, and all setup-generated Kubernetes resources.

Add `internal/releasepatch`:

```go
type Patch struct {
    RolloutUID      string
    ResourceVersion string
    Container       string
    PreviousImage   string
    CandidateImage  string
    PreviousSteps   json.RawMessage
    Lane            string
    Weights         []int
    Operations      []JSONPatchOperation
}
```

The JSON Patch contains tests for the observed resource version/current image followed by replacements at exactly:

```text
/spec/template/spec/containers/<selected-index>/image
/spec/strategy/canary/steps
```

For lane `[25, 50, 100]`, generated steps are `setWeight: 25`, indefinite pause, `setWeight: 50`, indefinite pause; Argo reaches 100% after the last promotion. Existing background analysis, Services, traffic router, pod template, replicas, probes, environment, secrets, ports, and resources remain byte-for-byte outside those paths.

Immediately before apply, re-read and compare:

- candidate source and digest;
- currently running image;
- `safelane.yml` content hash;
- selected Rollout UID/resourceVersion and the two patch source fields.

Any material change cancels the pending approval and returns to assessment. The approval is single-use and internally bound to Application, Environment, candidate, patch, configured analysis, and recommendation.

### 11. Execution and natural controls

Retain `internal/execute` and `internal/orchestrate` as the highest behavioral seam. Adapt them from full-bundle application to `releasepatch.Patch` and keep Argo as the single health/rollback authority.

The agent-facing internal command surface becomes:

```text
safelane inspect <env> [<revision>]
safelane recommend <env> <assessment-json-path|->
safelane run <env>
safelane status [<env>]
safelane hold <env> <reason>
safelane continue <env> <reason>
safelane stop <env> <reason>
safelane proof <env> [--details]
```

Six command surface rules make this cheap for Claude to call and pleasant for a person to type:

1. **No `release` prefix and no `--json` flag.** SafeLane is a release tool, so the noun is implied. Output is JSON when stdout is not a terminal and readable text when it is, so the agent path carries no flag at all and a person typing the same command gets something legible. `--json` exists only to force machine output at a terminal.
2. **The Environment is the positional argument.** It is the one thing every command needs and the one thing the user actually says, so `safelane status production` reads the way the request was made.
3. **The Application is inferred, never typed.** SafeLane resolves it from the current repository's Git origin against registered Applications. `--app <app>` exists only to disambiguate when that resolution is not unique, and its absence is not an error when exactly one Application matches.
4. **No release identifier is ever passed.** There may be only one active Release Attempt for an Application and Environment, so `recommend`, `run`, `status`, `hold`, `continue`, `stop`, and `proof` all resolve it from that pair. The previous `--release <internal-id>` flag contradicted the rule that identifiers stay internal.
5. **There is no `--yes` anywhere.** A flag the caller passes on every invocation is not a safety mechanism, and the agent would always pass it. A recommendation is advice, not authorization. At a terminal, `run` asks the contextual final question. On the agent path, a hidden adapter records the user's direct answer to that exact question before `run`; a piped `run` with no recorded approval refuses to mutate. The approval is bound and single-use, and the pre-apply recheck cancels it if any material fact moved. Registration likewise previews before a separate confirmed write, while `hold`, `continue`, and `stop` each require an explicit reason.
6. **The revision is a second optional positional, not a flag.** `safelane inspect production a1b2c3d` releases that exact commit; `safelane inspect production` uses the default-branch head. The revision is validated against the registered repository's default-branch history, so a bare value cannot be mistaken for anything else.

The only surviving flags are `--details` on `proof`, `--app` to disambiguate, and `--json` to force machine output at a terminal. Each changes behavior rather than confirming intent. `--details` in particular must stay opt-in: loading full proof by default would spend Claude's context on records nobody asked for.

Reasons are positional text on `hold`, `continue`, and `stop`, because a control without a recorded reason is not useful in proof.

Status answers with a named state rather than a progress guess, rendered as **A4** in Appendix A. The states are `assessing`, `awaiting_approval`, `applying`, `monitoring`, `paused`, `completed`, `failed`, and `stopped`. Every state also reports what it is waiting for: evidence, the user's approval, an Argo promotion, a background measurement, or nothing because it is terminal. The skill renders these in release language and never shows the state names.

When SafeLane's stored record and the observed Rollout disagree, the observed Rollout is authoritative. SafeLane reconciles its record to the cluster, reports the correction plainly, and never asks the user to decide which one to believe. This makes reconnecting to a release in progress a read rather than a replay.

At each indefinite pause, SafeLane waits for a new successful measurement from the configured background AnalysisRun before requesting the next Argo promotion. Analysis failure or Argo abort ends progression and is attributed to Argo. Hold pauses without widening exposure; continue requires explicit user intent; stop requests Argo abort/restore-stable and records the reason. Retry creates a new immutable attempt.

Replica-based weights are described as approximate exposure. Exact request-traffic measurement is not used in the POC assessment.

### 12. Compact history and detailed proof

Refactor `internal/store`, `internal/ledger`, and `internal/proof` to persist one release directory plus one compact append-only history file per Application/Environment.

`history.jsonl` cards contain only:

```go
type HistoryCard struct {
    At            time.Time `json:"at"`
    Candidate     string    `json:"candidate"`
    Recommendation string   `json:"recommendation"` // proceed | wait
    Lane          string    `json:"lane,omitempty"`
    Reason        string    `json:"reason"` // one short influential reason
    Outcome       string    `json:"outcome"`
}
```

The normal evidence view loads at most the ten newest same-Environment cards. Older or cross-Environment history is loaded only when Claude identifies a concrete relevance question. History may raise concern or strengthen confidence but never erases a known hazard and never changes risk arithmetically.

Each detailed release directory stores the frozen Release Delta, final Recommendation, approved Release Patch, append-only execution events, and terminal Release Proof. It does not store the conversation, abandoned assessment drafts, repeated diffs, normal tool traces, or any secret value excluded at the evidence boundary.

## Testing Decisions

### Primary seam

Use `internal/orchestrate.Coordinator` as the single high behavioral test seam. Its dependencies are typed `Source`, `OCI`, `Cluster`, `Store`, clock, and ID providers. Assessment arrives as a validated external value from the active Claude session; production code never spawns a model. CLI golden tests remain the second, presentation-facing seam.

Prefer external behavior over internal calls:

- a registration test begins with fake Git/Kubernetes observations and asserts the exact `safelane.yml` plus atomic/no-op/reconcile behavior;
- a release test begins with Application/Environment intent and asserts the frozen Delta, understandable evidence, selected configured lane, exact Patch, and stored proof;
- an execution test asserts only the selected image and steps changed in the Rollout;
- a control test addresses the active release by Application/Environment and asserts status/hold/continue/stop outcomes without requiring a visible ID.

### Module tests

- `internal/config`: schema validation, duplicate Environment/lane rejection, lane weight monotonicity/final 100, default mapping integrity, path derivation, atomic write, policy preservation, no-op reconciliation, and rejection of old files.
- `internal/discovery`: zero/one/many Rollouts, zero/one/many inline containers, namespace-only listing, current-context confirmation, missing Services/templates, background versus inline analysis, workloadRef, blue-green, GitOps detection, and official Argo fixture compatibility.
- `internal/verify/oci`: anonymous and Docker-credential auth, tag-to-digest resolution, multi-platform consistent/inconsistent labels, missing/malformed source metadata, tag enumeration, and non-GHCR registry behavior using an in-process OCI test registry.
- `internal/verify/github`: default-head resolution, explicit revision, exact-revision checks, missing branch protection, failed/pending build, no older fallback, complete base-to-head comparison, and unrelated histories.
- `internal/delta`: stable content hash, immutable views, bounded initial history, evidence-handle resolution, provided-evidence binding, prompt-injection strings preserved as inert data, and secret exclusion covering container environment values, `envFrom`, mounted Secret/ConfigMap contents, kubeconfig contents, registry credentials, and secret-bearing diff hunks.
- `internal/assessment`: strict schema, valid handles, observation grounding, required hazard causal fields, four coverage states, configured risk-to-lane mapping, Proceed/Wait only, no executable Wait, and invalid/undetermined correction behavior.
- `internal/releasepatch`: container-index selection, exact two-field JSON Patch, lane-to-step conversion, preservation of all unrelated Rollout fields, resource-version/current-value tests, and stale recheck rejection.
- `internal/execute`: background-analysis success per gate, missing measurements never pass, Argo failure attribution, terminal reconciliation, idempotent reconnect, and emergency controls.
- `internal/store`/`internal/proof`: one active release per pair, latest-ten history, immutable detailed records, no conversation/trace persistence, no secret values in any stored record, compact/detail agreement, and retry-as-new-attempt.
- CLI surface: Application inference from Git origin, `--app` required only when resolution is ambiguous, active-release resolution from the Application/Environment pair without an identifier, terminal versus piped output selection, optional positional revision defaulting to the default-branch head, `run` refusing without a proceeding recommendation and explicit contextual approval, reconnecting to an active attempt without reapplying, each named release state reporting what it is waiting for, and Rollout-wins reconciliation when the stored record disagrees with the cluster.

### Fixed assessment scenarios

Create `testdata/assessment/` fixtures and an evaluation runner outside the production runtime. Each scenario freezes the evidence views and validates structure, grounding, stopping behavior, question quality, recommendation direction, and approval isolation without requiring exact prose:

1. small, well-bounded candidate with complete evidence;
2. database migration without production-sized test evidence;
3. dependency/retry change with relevant prior latency failure;
4. documentation-only change;
5. failed candidate CI;
6. irrelevant history that must not influence the result;
7. large diff that is not automatically declared risky because of size;
8. prompt injection embedded in source, commit message, analysis name, and history;
9. an attractive but unsupported deployment claim;
10. the same change under Ahmed's replica-based demo and an official-Argo-shaped routed environment, without using exact-traffic accuracy as a POC risk input.

Assertions include:

- mandatory views read before optional investigation;
- zero questions on complete evidence;
- every question is material, singular, and explains why the missing fact matters;
- `I don't know` terminates that branch;
- no general code-review findings;
- no invented observations or evidence handles;
- every credible hazard has preconditions, consequence, and honest coverage;
- serious uncovered/unknown hazards do not yield an ordinary Proceed;
- eligibility failures never become semantic risk;
- no release mutation occurs before the contextual final approval;
- output uses plain release language and hides internal IDs/risk labels.

Tool traces may be retained by the evaluation runner for debugging, but production history does not store them and the POC does not add a trace-policy engine.

- `workloadRef` and advanced Argo Rollouts step/plugin types
- Exact request-traffic measurement or traffic-accuracy risk assessment
- Inventing or generating Application health analysis
- Conversational creation of custom lanes; advanced users may edit and revalidate YAML manually
- AI-generated setup configuration
- Slack integration
- General code review or broad security scanning
- Multiple assessor/critic agents
- A production prompt/tool-trace policy engine

- Flagger, Keptn, or non-Argo runtime integrations
- Migration, backward compatibility, or automatic deletion for old SafeLane files and commands
- Production hardening, multi-cluster federation, dashboard, HTTP API, or MCP server

## Further Notes

### Phase 2 research addendum: lessons from Stakpak

See [Stakpak workflow research and possible SafeLane Phase 2 adaptations](../research/stakpak-profiles-phase-two.md).

Three of that note's lessons are already absorbed into this POC because each is presentation or hardening over planned work rather than a new subsystem: the `/init`-shaped registration readiness summary in decision 3, the named release states plus the Rollout-wins authority rule in decision 11, and the secret-exclusion boundary in decisions 7 and 12. They do not change the definition of done or the out-of-scope list.

Carry forward after the locked POC is complete:

1. **Verified Release Context:** store only small, source-cited Application/Environment deployment facts that can eliminate repeated material assessment questions. Live evidence outranks remembered context, relevance controls loading, and context never authorizes mutation.
2. **Channel-neutral collaboration:** render the same frozen recommendation, status, health, and proof through a later Slack or scheduled adapter while keeping transport/destination separate from release behavior.
3. **Cross-interface recovery:** reconstruct an active release from its Release Attempt, execution events, recommendation, and proof rather than replaying conversation history.
4. **Conditional operating-mode experiment:** only when a second invocation surface exists, test built-in `release` and `watch` modes. `watch` has no controller credential or mutation path; `release` retains the exact POC approval. Modes do not live in `safelane.yml` and cannot select an Environment or Lane.

Do not add configurable Profiles, profile inheritance, automatic conversational memory, Rulebook policy, provider/model configuration, reusable approval, or Slack mutation before authenticated human identity can be bound to the exact frozen recommendation.

## Appendix A — Output contract

Every line SafeLane shows a person is fixed here. A ticket says *what* to build; this appendix says *exactly what it must print*. Implementation must copy these blocks rather than reinvent the wording, and must not change them to make a test pass. Values in the blocks are illustrative; the wording, order, and labels are the contract.

### A1 — Registration readiness summary

```text
Registered payments-api in production.

Releasing        container "payments-api" in Rollout "payments-api" (namespace payments)
Watching         background analysis "success-rate", checked by Prometheus
Will change      the container image, and the canary steps
Will not change  probes, resources, replicas, environment, secrets, ports, Services,
                 the traffic router, or your health analysis

Say "Deploy payments-api to production" when you are ready.
```

### A2 — Proceeding recommendation

```text
I recommend proceeding with this release.

Why it looks ready
✓ The version you want to release passed its required build and test checks.
✓ The container prepared for deployment came from that successful build.
✓ I reviewed everything changed since the currently running version and found nothing requiring additional release precautions.

Proposed rollout
Release to 50%, verify the configured health analysis, then continue to 100%.
Using your fast lane.

SafeLane will stay with the rollout. If the checks fail, Argo will stop it and restore the stable version.
```

### A3 — Waiting recommendation

```text
I recommend waiting on this release.

What concerns me
This change alters how payments-api writes to its database, and the schema migration runs
during start-up of the new version. If it fails part-way, the stable version cannot read
the rows that were already migrated.

What I could not confirm
Whether the migration has been run against production-sized data.

What your health analysis would not catch
Your configured analysis measures request success rate over two minutes. A migration that
completes but leaves rows unreadable would not appear there.

Next step
Run the migration as a separate job before this release, or tell me it already ran and I
will reassess.
```

### A4 — Status lines

One line per state. The state name itself is never shown.

```text
assessing          Reading everything changed since the running version.
awaiting_approval  Waiting for you to approve the rollout to production.
applying           Applying the approved image and canary steps.
monitoring         At 50%. Waiting for the next health measurement.
paused             Held at 25% at your request: "waiting for the on-call handover".
completed          Released at 100%. Stable since 14:12.
failed             Argo stopped the rollout at 50% and restored the stable version.
stopped            Stopped at your request: "customer reported errors". Stable version restored.
```

### A5 — The approval question

Printed immediately after A2, and never without it.

```text
I will change the container image and the canary steps. Your probes, resources, replicas,
environment, secrets, ports, Services, traffic router, and health analysis stay exactly as
they are.

Proceed with this rollout to production?
```
